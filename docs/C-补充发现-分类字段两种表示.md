## 1. 现象（同一个字段，两种含义）

| 来源 | `category` 实际存的 | 证据 |
|---|---|---|
| **手动录入表单** | **前缀键**（`C` / `R` / `L` / `Q` …）✗ | `renderer/pages/parts_editor.js` L82：`for (const option of M.CATEGORY_OPTIONS)` → 选项的 `key` 就是前缀（`parts_model.js`：`{ key: "R", label: "电阻" }`）✓ 所以你在界面选了「电阻」，**落库的是 `R`** ✗ |
| **对账单入库** | **立创中文商品类型**（`贴片电阻` / `排母` / `MOSFET`…）✗ | 你库里 p_0002~p_0025 的 `category` 全是中文名 ✓（`厚膜电阻`行存的是 `贴片电阻` ✓） |

⇒ 你自己手录的那条 **`p_0026` 的 `category` 就是 `R`** ✗，而同样是 100 kΩ 0603 ±1% 的
对账单条目（p_0006）存的是 **`贴片电阻`** ✗ —— **同一个字段、两种写法** ✗。

## 2. 为什么这比"分类不全"更要紧

1. **低库存阈值语义混乱** ✗：`R` 在前缀表里有默认阈值 ✓，`贴片电阻` 走 `_default` ✓
   → 同一类料**标准不同** ✓（你会觉得"提示时灵时不灵"✓）
2. **界面显示不一致** ✗：库存表里一列混着 `R` 和 `贴片电阻` ✓
3. **合并/判定链路** ✗：`dedupe_key` 不含 `category` ✓ 所以还不至于合不上 ✓，
   但**阈值、导出、按分类筛选**都受影响 ✓
4. **C 若只加分类** ✗：加完仍是"前缀键 + 立创名"两套 ✓ → **等于把问题扩大一倍** ✗

## 3. 三个可选方案（**请你选一个**）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **① 统一为立创中文名**（推荐 ✓） | `category` 一律存**中文分类名**（`贴片电阻` / `排母` / `MOSFET`…）；前缀键只作为**阈值映射的内部键**，不落库 ✗ | 与对账单天然一致 ✓ 界面可读 ✓ 与立创商品类型对得上 ✓ | 需**一次性迁移**已有数据的 `R`→`贴片电阻` 等 ✓ + 改表单/阈值表/导出/测试 ✓ |
| ② 统一为前缀键 | `category` 一律存 `R`/`C`/`PINHDR`…；对账单路径做「中文名 → 键」映射 ✓ | 阈值直接命中 ✓ | 界面可读性差 ✗ 新增类要造键（`ALCAP-SMD` 这种）✓ 与供应商名称脱节 ✗ |
| ③ 两个字段并存 | `category`（中文名）+ `threshold_key`（键）各存一个 ✓ | 语义最清楚 ✓ 阈值最准 ✓ | 数据模型变更最大 ✗ 所有引用点都要改 ✓（plan §4/§6 + 迁移 + 测试 ✓） |

> 我的建议：**①**（够用且改动可控 ✓）。若你希望"分类"与"阈值键"彻底分开，就选 **③**（更干净，但工作量大一倍 ✓）。

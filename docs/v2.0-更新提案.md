## 1. 一句话目标

在**保留"默认完全离线"**的前提下，新增：**多个仓库**（本机仓库 + 云同步仓库）**均可视**，
可**从云仓库取料**，但**只能导入到本地仓库**（云仓库对它**只读**）。

## 2. 为什么这是"大版本"（v1 → v2）

| 被触动的东西 | v1（现状） | v2（提案） |
|---|---|---|
| **离线承诺** | spec FR-6.1：**完全离线**，源码零网络调用（有测试逐字钉住） | **默认完全离线**；云功能需**用户显式开启**，开启后仅访问**你配置的那一个**云地址 |
| **验收标准** | AC-6 多行断言"没有任何对外请求" | 改为"**未开启云功能时零请求**（可断言）+ 开启后仅白名单地址 + 每次请求有审计记录" |
| **数据模型** | 单库（`data/parts.json` 等三个文件） | `settings.json` 增 `warehouses[]` + `active_warehouse`；每个仓库**各自独立**三个文件 |
| **IPC 契约** | 18 个通道 | 增云与仓库相关通道（见 §5），并写入 plan §6 |
| **数据安全边界** | 库只在本机 | 库可能被推到云端 ✗ → **默认只往回拉，不往外推**（见 §4 权限模型） |

**结论**：因为改了"核心承诺 + 数据模型 + 契约"三样，按项目惯例应记 **v2.0** ✓。

## 3. 不变的底线（提案里明确保留）

1. **离线优先**：不开云功能 == 现在的 v1 行为，**一模一样** ✓（不联网、不检查更新、不弹窗）
2. **入库必须人工核对** ✗ 不提供"一键静默导入" ✓（FR-1.3 继续有效）
3. **数量变动一律留痕** ✓（FR-4.5 继续有效；跨仓库导入也要写 `movements.json`）
4. **比对只读** ✓（FR-2.5 继续有效）
5. **危险操作双层闸门** ✓（按钮 disabled + 服务端拒绝）

## 4. 核心设计

### 4.1 仓库（warehouse）模型

```
仓库 = { id, name, kind, path | cloud, last_sync_at, read_only, note }
kind: local   本机仓库（可读可写；就是现在的 data/）
      cloud   云仓库（**只读**：可取料，不能导入）
      mirror  本地 + 云同步（本机文件为主，云端是同一仓库的同步副本）
```

- **多个仓库可同时存在**，界面顶部一个**仓库切换器**（可视 ✓：名称 + 类型徽标 + 同步时间）
- 每个仓库**独立** `parts.json` / `movements.json` / `settings.json`（不共用 ✗ 免得串数据）
- 切换仓库 = 切换整套数据；**跨仓库唯一的例外是"取料"**（云 → 本地 ✓）

### 4.2 权限模型（你要求的那条，落成机制）

| 动作 | 本地仓库 | 云仓库 | mirror |
|---|---|---|---|
| 浏览 / 比对 / 导出 | ✅ | ✅ | ✅ |
| 入库 / 领料 / 编辑 / 删除 | ✅ | ❌ **禁止** | ✅（写本机） |
| **取料（导入本地）** | — | ✅ **唯一允许的方向** | ✅ |
| 把本地库**推**到云 | ❌ 默认**不做** | — | ⚠️ 需你单独开启（见 §6 开放问题） |

**两层闸门**（沿用项目惯例）：
- 界面：云仓库处于"只读模式"时，入库/编辑类按钮一律 `disabled` + 顶部徽标写"云仓库（只读）"
- 服务端：所有写通道在**入口**校验 `active_warehouse.read_only === true` → 直接 `{ ok:false, error:"云仓库只读：只能从云仓库取料并导入本地仓库" }`

### 4.3 取料流程（与既有核对表语义一致 ✓）

```
选云仓库 → 搜索（值/封装/型号/分类）→ 结果列表（每条标明来源：仓库名 + 云端 id + 快照时间）
        → 选中若干条 → **人工核对表**（复用现有核对表的"命中/疑似/新增"三桶语义 ✓）
        → 目标仓库固定为"当前本地仓库"（不可选 ✗）→ 确认导入
        → 写本机 parts.json + movements.json（ref = cloud:<warehouse_id>:<item_id>，留痕可追溯 ✓）
```

- 冲突判定**复用 `dedupe_key`**（值·封装·耐压·材质·容差 ✓ 全工程唯一实现）
- 疑似（云端那条与本地某条"像是同一个料"）→ **必须人工裁决** ✓ 不自动合并
- 导入**只补空不覆盖** ✓（沿用 `mergePartInfo` 语义）

### 4.4 云服务器与端口（你要的"云服务器链接端口"）

界面（设置页 → 云）：

| 字段 | 示例 | 说明 |
|---|---|---|
| 服务器地址 | `https://your-host` | 建议 HTTPS ✓；自测可 `http://127.0.0.1` |
| **端口** | `8443` | 单独一项 ✓ 留空则按协议默认（443/80） |
| 路径前缀 | `/api/v1` | 便于反向代理 |
| 令牌 | （写入后不回显） | **存放位置待定**（§6 问题 3） |
| 超时 / 重试 | `5000 ms` / `1 次` | 超时即明确报错，不静默重试 |
| 开关 | 关（默认） | **开启前整个应用行为与 v1 完全一致** ✓ |

**服务端接口契约（草案，供你自建或采购）**：

```
GET  {base}/health                      → { ok, name, version, time }
GET  {base}/warehouses                  → { ok, warehouses:[{ id, name, item_count, updated_at }] }
GET  {base}/warehouses/{id}/items?q=..&limit=..&offset=..  → { ok, items:[...], total }
GET  {base}/warehouses/{id}/items/{item_id}                → { ok, item }
```

- 只需要这 4 个**只读**接口 ✓（因为"只能给本地仓库导入" ✓）
- 若以后要"推送到云"，再加 `POST/PUT` 并**单独开关** ✓
- 认证：`Authorization: Bearer <令牌>`（草案 ✓ 见 §6 问题 4）

### 4.5 主进程唯一出口（沿用我们此前讨论的方案 ✓）

```
渲染层（保持零网络 ✗ 不放宽 CSP connect-src）
   ↓ window.api.cloudPull({ warehouse_id, query })
主进程 services/cloud_client.js —— 唯一出口：地址白名单（= 你配置的那一个）+ 超时 + 限速 + 审计
   ↓ Electron 自带 https（零 npm 依赖 ✓）
你的云服务器
```

- **域名白名单**只有一处（AGENTS 标准做法④），非白名单一律拒绝 ✓
- **不得关闭证书校验** ✗
- 每次请求写**本地审计**（时间/地址/参数/结果/耗时）→ 你事后能查"它到底联了什么" ✓
- 云不可达时：**明确提示 + 本地功能完全不受影响** ✓（离线降级）

## 5. IPC 契约增量（草案，待并入 plan §6）

| 通道 | 方向 | 说明 |
|---|---|---|
| `warehouse:list` | 读 | 列出所有仓库 + 当前活动仓库 |
| `warehouse:add` / `warehouse:switch` / `warehouse:remove` | 写 | 增删切换（remove 不删数据 ✗ 只出列表，需确认 ✓） |
| `cloud:status` | 读 | 云开关 / 地址 / 连通性 / 上次同步 |
| `cloud:test` | 写 | 点"测试连接"（只打 `/health`） |
| `cloud:pull` | **读** | 从云仓库取料 → 返回**建议清单**（不落库 ✓） |
| `cloud:import` | 写 | 按人工决定把取到的料导入**当前本地仓库** ✓ |

> 关键：`cloud:pull` 与既有 `statement:parse` 一样**只读返回建议** ✓，
> 真正落库只发生在 `cloud:import` 且必须带人工决定 ✓（与现有两条入库路径同一套模式 ✓ 反重复规则 ✓）。

### 11.2 修订后的同步模型（关键）

**核心不变**：入库仍必须人工核对 ✓、数量变动一律留痕 ✓、离线优先 ✓。
**新的事实**：云服务器是"**各仓库实时数据的汇聚点**" ✓。

由此得到一个**不需要冲突合并**的设计 —— 直接复用了项目已有的最强约束 ✓：

```
每台机器的每次数量变动 → 一条不可变的 movements 记录（v1 已有 ✓，带 origin 设备号）
本地写入立即可用（离线照常 ✓）
联网后：把本地新增的 movements 推上去（按 id 去重，append-only ✓）
        把别处的 movements 拉下来，追加到本地
        → 库存量由 movements 推导/校正（同一套规则，可重算 ✓）
```

- **为什么这样不冲突**：movements 是**只追加**的 ✓ —— 两个人同时入库，产生的是**两条不同记录**，不是同一条记录的两种版本 ✓ → 合并就是"并集" ✓（幂等：同 id 重复推送只算一次 ✓）
- **并发的扣减**：出库超库存的判断要**对"已同步的合并视图"**做（本地未同步的扣减先记下 ✓，同步后重算并**明确提示**"已按最新库存校正"✓，必要时列出被影响的记录 ✓）
- **器件元数据（值/封装/阈值等）**：不属于 append-only ✗ → 冲突时**不自动覆盖** ✓，进入**人工裁决**（直接复用现有的"疑似"三桶语义 ✓ 反重复规则）
- **服务器"实时"的含义**：客户端一联网就推 ✓ + 服务端保存**每个仓库的合并视图**（按 movements 推导 ✓）→ 打开网页/换台机器即可看到最新 ✓
- **离线保证**：同步失败**绝不影响**本地任何操作 ✓（只是待同步队列变长 ✓，界面上给一个"待同步 N 条"的提示 ✓）

### 11.3 服务端（我给你一个可部署的单文件实现）

- **形态**：单文件 Node `http` 服务 ✓（**零 npm 依赖** ✓ 与项目一致 ✓）＋ 一个 JSON 数据目录（原子写：临时文件 → rename ✓ 沿用 `store.js` 的做法 ✓）
- **接口**（只读部分保留 §4.4；新增同步部分）：

```
GET  {base}/health                                  连通性
GET  {base}/warehouses                              各仓库概览（含 item_count / updated_at / 待同步条数）
GET  {base}/warehouses/{id}/items?q=&limit=&offset= 取料用（只读）✓
GET  {base}/warehouses/{id}/movements?since=<seq>   拉取增量（append-only ✓ 幂等）
POST {base}/warehouses/{id}/movements               推送本地新增（按 id 去重 ✓）
GET  {base}/warehouses/{id}/parts?since=<seq>       拉取元数据变更（冲突 → 人工裁决）
POST {base}/warehouses/{id}/parts                   推送元数据（服务端标记冲突，不自动覆盖 ✓）
```

- **认证**：`Authorization: Bearer <令牌>`（每台机器一个令牌 ✓ 可单独吊销 ✓）
